# Протокол treenity

**Русский** | [English](../eng/protocol.md)

Документ описывает «на проводе» и логику всех слоёв. Реализация:
`src/mac/frame.[ch]`, `src/mac/dupcache.[ch]`, `src/link/neighbor.[ch]`,
`src/link/beacon.c`, `src/routing/routing.[ch]`, `src/api/treenet.c`.

## 1. Формат кадра

Каждый кадр начинается с фиксированного заголовка 20 байт, передаваемого как
«сырые» байты (без схемы сериализации) для минимизации времени в эфире.
Многобайтовые поля — little-endian.

| Смещение | Размер | Поле | Назначение |
|---|---|---|---|
| 0 | 1 | `ver_type` | версия (старший ниббл) + тип кадра (младший ниббл) |
| 1 | 1 | `flags` | флаги (см. ниже) |
| 2 | 4 | `src` | адрес исходного отправителя (не меняется при пересылке) |
| 6 | 4 | `dst` | конечный получатель или broadcast |
| 10 | 2 | `seq` | порядковый номер исходного отправителя |
| 12 | 2 | `net_id` | идентификатор сети |
| 14 | 1 | `hop_limit` | оставшееся число переходов |
| 15 | 1 | `sec` | точка расширения безопасности / резерв |
| 16 | 4 | `prev` | адрес непосредственного передатчика (перезаписывается MAC) |
| 20 | N | `payload` | полезная нагрузка |
| 20+N | 2 | `crc` | CRC-16 (трейлер, только при `TREENET_ENABLE_FRAME_CRC`) |

### Контроль целостности (CRC-16)

При включённом `TREENET_ENABLE_FRAME_CRC` (по умолчанию) каждый кадр несёт
2-байтовый трейлер — CRC-16/CCITT-FALSE (полином `0x1021`, init `0xFFFF`, без
отражения, без финального XOR). CRC покрывает **весь заголовок, включая
перезаписанное поле `prev`, и полезную нагрузку**.

- Отправитель: `tn_frame_encode` считает CRC после формирования заголовка и
  payload и добавляет его в конец.
- Получатель: `tn_frame_decode` **до разбора полей** проверяет CRC; при
  несовпадении кадр молча отбрасывается (`frames_dropped++`), состояние не
  меняется.
- Стоимость: +2 байта на кадр; вычисление — nibble-таблица (16 записей),
  без 256-байтовой таблицы.
- **Совместимость:** значение должно совпадать на всех узлах сети. Узлы с
  разными настройками не поймут друг друга.

Дополнительно, помимо CRC, парсер отклоняет семантически некорректные кадры
(см. «Защита от повреждённых кадров» в конце документа).

### Флаги (`flags`)

| Бит | Имя | Значение |
|---|---|---|
| 0x01 | `TN_FLAG_WANT_ACK` | запросить hop-by-hop подтверждение |
| 0x02 | `TN_FLAG_FLOOD` | кадр распространяется flooding-ом |
| 0x04 | `TN_FLAG_FRAG` | payload начинается с заголовка фрагмента |
| 0x08 | `TN_FLAG_SEC` | payload защищён (точка расширения) |

### Поле `prev` — ключевая деталь

`src` всегда указывает на **исходного** отправителя и не меняется при
ретрансляции. `prev` при каждой передаче перезаписывается MAC-слоем на адрес
текущего передатчика (`tn_tx_submit`). Это позволяет:

- адресовать hop-by-hop ACK непосредственному отправителю (`prev`);
- устанавливать маршрут «вниз» через узел, от которого реально пришёл кадр;
- корректно оценивать качество связи именно с соседом (`prev`), а не с
  источником многошагового пакета.

## 2. Типы кадров

| Тип | Имя | Назначение |
|---|---|---|
| 0 | `TREENET_FRAME_BEACON` | link-local «hello»: Rank, родитель, интервал |
| 1 | `TREENET_FRAME_DATA` | одноадресный датаграмм приложения |
| 2 | `TREENET_FRAME_ACK` | подтверждение на один переход |
| 3 | `TREENET_FRAME_FLOOD` | широковещательная датаграмма (managed flooding) |
| 4 | `TREENET_FRAME_PROBE` | запрос beacon-ов (поиск родителя) |
| 5 | `TREENET_FRAME_DAO` | анонс маршрута «вниз» |

### Payload beacon (9 байт)

| Смещение | Размер | Поле |
|---|---|---|
| 0 | 2 | `rank` отправителя |
| 2 | 4 | `parent` отправителя (или `0xFFFFFFFF`) |
| 6 | 1 | `flags` (бит 0 `TN_BEACON_HAS_PARENT` — предлагает путь к Master) |
| 7 | 2 | `interval_100ms` — текущий интервал beacon-ов в единицах 100 мс |

Интервал передаётся, чтобы сосед мог точно посчитать ожидаемое число beacon-ов
между двумя приёмами и не принять растущий интервал Trickle за потери.

### Payload DAO (5 байт)

| Смещение | Размер | Поле |
|---|---|---|
| 0 | 4 | `origin` — узел, для которого строится маршрут |
| 4 | 1 | `hops` — число переходов от `origin` |

### Заголовок фрагмента (4 байта)

| Смещение | Размер | Поле |
|---|---|---|
| 0 | 2 | `dgram_id` — идентификатор датаграммы |
| 2 | 1 | `index` — номер фрагмента (с 0) |
| 3 | 1 | `count` — всего фрагментов |

## 3. MAC-слой

### 3.1 CSMA/CA

Перед передачей кадр ставится в слот (`tn_tx_submit`) и планируется на
`now + delay + backoff`, где `backoff = random(0..TREENET_CW_MAX) *
TREENET_SLOT_MS`. При `tn_tx_poll`:

1. если слот надёжный и исчерпал попытки — освобождается и генерируется
   событие `TX_FAILED`;
2. если порт дал `channel_free` и эфир занят — попытка откладывается на слот;
3. иначе кадр передаётся через `port.tx`.

### 3.2 Кэш дубликатов

`tn_dupcache_seen(src, seq, now)` хранит недавно виденные пары `(src, seq)` в
хеш-таблице фиксированного размера с TTL `TREENET_DUP_TTL_MS`. Используется
для подавления повторов при пересылке и flooding.

> Важно: при получении дубликата надёжного кадра ACK всё равно отправляется
> повторно, чтобы отправитель прекратил ретрансляции.

### 3.3 Hop-by-hop ACK

- Получатель кадра с флагом `WANT_ACK` отвечает кадром `ACK` на адрес `prev`.
- `ACK` использует поле `seq` для переноса подтверждаемого номера.
- Отправитель сопоставляет ACK по паре `(ack_dst, ack_seq)` со своим слотом и
  освобождает его (событие `TX_DONE`).
- При отсутствии ACK кадр передаётся повторно, всего до
  `TREENET_MAX_RETRIES` передач.

### 3.4 Время в эфире

`tn_airtime_estimate_us()` считает время в эфире LoRa по формуле Semtech
AN1200.13 (SF, BW, CR, преамбула, CRC). Если LoRa-параметры не заданы,
используется консервативная линейная оценка. Накопленное время — в
`stats.airtime_ms`. Это основа для будущего контроля duty-cycle.

### 3.5 Фрагментация

Датаграммы больше `TREENET_MTU - TN_FRAME_OVERHEAD` разбиваются на фрагменты с
заголовком `FRAG` (флаг `TN_FLAG_FRAG`). Сборка — по слотам
`TREENET_REASSEMBLY_SLOTS` с битовой маской принятых фрагментов; по готовности
датаграмма отдаётся в `on_recv`. Максимум фрагментов —
`TREENET_MAX_FRAGMENTS`.

## 4. Link-слой

### 4.1 Beaconing (Trickle)

- Интервал `I` начинается с `TREENET_BEACON_MIN_MS` и удваивается после каждой
  передачи до `TREENET_BEACON_MAX_MS`.
- Передача планируется в случайный момент второй половины интервала
  (`[I/2, I)`), чтобы узлы не синхронизировались.
- Выбор/смена родителя сбрасывает `I` к минимуму (`tn_beacon_reset`,
  вызывается из `routing_set_parent`), чтобы соседи быстрее узнали новый
  Rank и маршрут — это ускоряет реконвергенцию.
- Beacon не пересылается (`hop_limit = 1`).

> **Критично:** `TREENET_BEACON_MAX_MS` должен быть меньше
> `TREENET_PARENT_TIMEOUT_MS` и `TREENET_NEIGHBOR_TIMEOUT_MS` (запас ×3).
> Иначе узел будет считать здорового соседа мёртвым в паузе между beacon-ами и
> начнётся флаппинг. Значения по умолчанию согласованы: 20 с против 60/90 с.

### 4.2 Оценка качества связи (LQI)

Для каждого соседа:

- **RSSI, SNR** — EWMA (фактор 1/8) по всем принятым кадрам.
- **PDR** — по beacon-ам: между двумя приёмами ожидается
  `elapsed / advertised_interval` beacon-ов; все «пропущенные» периоды
  добавляются как нули, текущий — как 256. EWMA даёт гладкую доставку.
- **ETX** = `256·256 / PDR` (Q8; 256 == 1.0).
- **Стоимость связи** (`link_cost`):

  ```
  snr_score = f(SNR)          # 0..1024, 0 — идеал, 1024 — на пределе
  etx_pen   = clamp(ETX_q8-256, 0, 768)   # 0 при ETX 1.0, 768 при ETX 4.0
  link_cost = (W_SNR·snr_score + W_ETX·etx_pen) / 256
  ```

  Метрика ETX доминирует: это заставляет предпочитать качественный двухшаговый
  путь одному «плохому» линку.

## 5. Routing-слой

### 5.1 Rank и DODAG

- Master: Rank = 0, родителя нет, всегда `connected`.
- Узел: `rank = parent.rank + TREENET_RANK_STEP + link_cost(parent)`. Шаг
  (`TREENET_RANK_STEP`, по умолчанию 8) гарантирует строгий рост Rank вдоль
  пути, что исключает петли.
- `TREENET_RANK_INFINITE` (0xFFFF) — «пути нет».

### 5.2 Целевая функция и выбор родителя

Кандидат — сосед, который:
- «свежий» (получали beacon не позже `TREENET_PARENT_TIMEOUT_MS`);
- объявляет `TN_BEACON_HAS_PARENT` (сам имеет путь к Master);
- даёт конечный `candidate_rank = n.rank + RANK_STEP + n.link_cost`.

Выбирается кандидат с минимальным `candidate_rank`. Если кандидатов нет —
узел теряет родителя (`ROUTE_LOST`/`DISCONNECTED`).

### 5.3 Гистерезис и dwell-time

Смена родителя происходит, если:
- текущий родитель «мёртв» или недоступен, **или**
- прошёл `TREENET_PARENT_DWELL_MS` с момента выбора текущего родителя, **и**
  `best_rank < cur_rank · (100 − H)/100`, где `H` —
  `TREENET_PARENT_HYSTERESIS_PCT` (по умолчанию 25 %).

Это устраняет флаппинг при фединге, но сохраняет быстрое восстановление при
реальном отказе.

### 5.4 Loop avoidance

За счёт строгого роста Rank родитель всегда имеет Rank меньше, чем ребёнок.
Потенциальные петли дополнительно режутся проверкой
`candidate_rank < 0xFFFF` и тем, что потомок всегда имеет больший Rank.

### 5.5 Маршруты «вниз» (storing mode) и DAO

- При (пере)выборе родителя узел отправляет `DAO` вверх.
- DAO идёт к родителю, при этом `src = origin` сохраняется, `prev` — текущий
  передатчик.
- Каждый промежуточный узел, приняв DAO, ставит маршрут
  `dst = origin, next_hop = prev` и пересылает DAO своему родителю; Master тоже
  ставит маршрут и останавливается.
- Так каждый предок получает маршрут до всех узлов своего поддерева.
- DAO передаётся надёжно (`WANT_ACK`), чтобы маршруты не терялись на зашумлённом
  канале.
- Периодическое обновление — раз в `TREENET_ROUTE_REFRESH_MS`; запись истекает
  через `TREENET_ROUTE_TIMEOUT_MS`.
- При потере соседа все маршруты через него удаляются
  (`tn_route_remove_via`).

### 5.6 Восстановление маршрута

При потере родителя узел немедленно пытается выбрать нового (`select_parent`).
Если кандидатов нет, периодически рассылает `PROBE` (broadcast, `hop_limit=1`),
на который соседи отвечают немедленным beacon-ом.

## 6. Пересылка данных

### 6.1 Выбор следующего перехода

`tn_route_next_hop(dst)`:
1. `dst` — прямой сосед → отправляем ему (он доставит, петли нет);
2. иначе — маршрут из таблицы «вниз» (`next_hop`);
3. иначе — родитель (движение вверх, достигает любого предка, включая Master).

### 6.2 Одноадресная доставка

`DATA` с конечным `dst`. Каждый узел:
- если `dst == я` → (при `WANT_ACK`) ACK в `prev`, затем доставка в `on_recv`;
- иначе — проверка дубликата, декремент `hop_limit`, отправка следующему
  переходу. При `WANT_ACK` ACK отправляется и на промежуточных узлах
  (подтверждение на каждом переходе).

### 6.3 Управляемый flooding (broadcast)

`FLOOD` с `dst = broadcast`:
- проверка дубликата;
- локальная доставка в приложение;
- ретрансляция с задержкой, зависящей от SNR принятого кадра: **слабый линк
  (низкий SNR) ретранслирует раньше**, сильный — позже. Это распространяет
  сообщение наружу прежде, чем его продублирует плотное ядро.
- Роль `REPEATER` ретранслирует с нулевой задержкой.

## 7. События и статистика

События (`on_event`): `NETWORK_READY`, `JOINED`, `PARENT_CHANGED`,
`NEIGHBOR_ADDED`, `NEIGHBOR_REMOVED`, `ROUTE_LOST`, `TX_DONE`, `TX_FAILED`,
`DISCONNECTED`.

Счётчики (`treenet_stats`): `frames_tx/rx/dropped`, `retransmissions`,
`beacons_tx/rx`, `parent_changes`, `datagrams_tx/rx`, `airtime_ms`.

## 8. Защита от повреждённых кадров

Помимо CRC, библиотека проверяет структурную и семантическую корректность и
**никогда не меняет состояние по некорректному кадру**:

| Уровень | Проверка |
|---|---|
| Кадр | длина ≥ `TN_FRAME_OVERHEAD`; CRC совпадает; версия протокола; `src != 0/broadcast`; `dst != 0` |
| Приём | `net_id` совпадает; `src != собственный адрес` |
| Beacon | payload ≥ 9; объявленный интервал в `[BEACON_MIN/2 .. BEACON_MAX]`; `parent != src`; при флаге `HAS_PARENT` — `rank < INFINITE` |
| DAO | payload ≥ 5; `origin != 0/broadcast`; `hops ≤ MAX_HOPS`; `prev != 0/broadcast` |
| Фрагмент | payload ≥ 4; `count ∈ [1..MAX_FRAGMENTS]`; `index < count`; не-последний фрагмент полного размера; одинаковый `count` у всех фрагментов датаграммы; `offset+len ≤ MAX_DATAGRAM` |
| Тип кадра | неизвестный тип → отброшен |

Любое нарушение → `frames_dropped++`, состояние (соседи, родитель, Rank,
маршруты) не изменяется. Повреждённый beacon не может «приманить» узел к
фиктивному родителю, повреждённый DAO — установить ложный маршрут.
