# Архитектура treenity

**Русский** | [English](../eng/architecture.md)

## 1. Цели и ограничения

**Цели**

1. Mesh-сеть с единым корнем **Master**, которая сама строится и
   перестраивается под лучшее качество связи.
2. Полная абстракция от железа: библиотека ничего не знает о МК, радио, RTOS
   и ОС. Всё железо — через порт.
3. Переносимость: C99, отсутствие динамической памяти, отсутствие зависимостей
   от платформы, кроме `string.h`/`stdint.h`.
4. Учёт качества канала по RSSI/SNR каждого принятого кадра.

**Ограничения**

- Целевой масштаб: 100–1000 узлов на один Master.
- Транспорт по умолчанию — LoRa, но библиотека не привязана к модему.
- Безопасность в v1 не реализована, но заложены точки расширения
  (`TN_FLAG_SEC`, поле `sec` в заголовке, `TREENET_ENABLE_SECURITY_HOOKS`).

## 2. Слои

```
┌──────────────────────────────────────────────────────────┐
│ Приложение: treenet_send / treenet_broadcast / колбэки    │
├──────────────────────────────────────────────────────────┤
│ Routing  (src/routing): DODAG, Rank, Objective Function,  │
│          выбор родителя, DAO, таблица маршрутов вниз      │
├──────────────────────────────────────────────────────────┤
│ Link     (src/link):    beaconing (Trickle), таблица      │
│          соседей, оценка LQI (RSSI/SNR/PDR/ETX/стоимость) │
├──────────────────────────────────────────────────────────┤
│ MAC      (src/mac):     кодек+CRC, CSMA/CA, dup-cache,    │
│          фрагментация, время в эфире, ACK                 │
├──────────────────────────────────────────────────────────┤
│ Core     (src/core):    ring-buffer, таймеры, EWMA,       │
│          очередь событий, утилиты, контекст               │
├──────────────────────────────────────────────────────────┤
│ PORT     (реализует пользователь): tx/now_ms/rnd/...      │
│          приём: treenet_rx(buf, len, rssi, snr)           │
└──────────────────────────────────────────────────────────┘
```

Слои связаны через единый контекст `struct treenet` (см. `src/core/internal.h`)
и не используют динамическую память.

## 3. Модель памяти

- Вся память выделяется вызывающей стороной: `treenet_init(void *storage,
  size_t size, ...)`. Размер — `treenet_context_size()`.
- Внутри контекста находятся фиксированные массивы:
  - таблица соседей (`TREENET_MAX_NEIGHBORS`, по умолчанию 32);
  - таблица маршрутов вниз (`TREENET_MAX_ROUTES`, по умолчанию 128);
  - кэш дубликатов (`TREENET_DUP_CACHE_SIZE`, 64);
  - очередь кадров на передачу (`TREENET_TX_QUEUE_SIZE`, 8);
  - кольцевой буфер приёма (`TREENET_RX_RING_BYTES`, 1024 байта);
  - слоты сборки фрагментов (`TREENET_REASSEMBLY_SLOTS`, 2);
  - очередь событий (`TREENET_EVENT_QUEUE_SIZE`, 16).
- `malloc` не используется нигде. `free` тоже.

> **Память Master.** В режиме storing (по умолчанию) каждый узел хранит
> маршрут до каждого узла своего поддерева. Для Master сети из 1000 узлов
> поднимите `TREENET_MAX_ROUTES` до `1024`. Обычным листьям достаточно
> значения по умолчанию.

## 4. Модель времени

- Время — монотонные миллисекунды от `port.now_ms()`, тип `uint32_t`.
- Все сравнения времени wrap-safe (`tn_time_after`, `tn_elapsed`), переполнение
  раз в ~49 дней обрабатывается корректно.
- Таймеры (`tn_timer_t`) не используют прерывания: они проверяются внутри
  `treenet_poll()`.
- **Tickless.** Периодические процессы (истечение маршрутов, старение соседей,
  очистка сборки фрагментов, DAO-refresh, PROBE) выражены не фиксированным
  тиком, а **вычисляемыми дедлайнами**. В конце каждого `treenet_poll()`
  библиотека сообщает порту ближайший дедлайн через опциональный
  `port.timer_arm(delay_ms)`, чтобы MCU спал до нужного момента.

## 5. Модель потоков и ISR

Библиотека **однопоточная**, но приём спроектирован для вызова из прерывания.

- **Один контекст для `treenet_poll()`.** Всё состояние (соседи, маршруты,
  родитель, слоты передачи, события) изменяется только внутри `poll`. Вызов
  `poll` из двух контекстов (например, из таймер-ISR и из main) недопустим —
  библиотека не реентерабельна.
- **`treenet_rx()` — из прерывания модема.** Кольцевой буфер приёма —
  **lock-free SPSC**: ровно один производитель (`treenet_rx`) и один потребитель
  (`poll`); критические секции не нужны. Функция лишь копирует кадр в буфер.
- **`treenet_send`/`treenet_broadcast` и интроспекция** — из того же контекста,
  что и `poll` (иначе гонки на слотах передачи/маршрутах и «рваные» чтения).
- **Инстансы независимы** — в библиотеке нет глобального состояния, поэтому
  разные контексты можно вести из разных потоков, если потокобезопасен порт.
- **Целевые MCU — 32-битные** (и шире): lock-free требует атомарных индексов
  размером в слово; проверка выполняется на этапе компиляции (`config.h`).
- **Порядок памяти.** Производитель публикует запись с release-барьером, а
  потребитель читает с acquire-барьером (`TN_PUBLISH`/`TN_CONSUME` в `util.h`);
  на слабоупорядоченных ядрах это даёт аппаратный барьер (DMB). Поэтому кольцо
  безопасно на многоядерных MCU (например, ESP32) **при условии** соблюдения
  правила один производитель / один потребитель.
- `treenet_poll()` вызывать достаточно часто (10–100 мс) либо по `timer_arm`
  (tickless).

**Многопоточность: синхронизирует вызывающий.** Если приложение вызывает
библиотеку из нескольких потоков/задач, оно само сериализует **не-ISR** точки
входа **своим мьютексом**:

- под мьютексом: `treenet_poll`, `treenet_send`, `treenet_broadcast` и
  интроспекция (`treenet_neighbors`, `treenet_stats`, ...);
- **вне мьютекса**: `treenet_rx` (из ISR; ринг lock-free, брать лок в прерывании
  нельзя).

Правила: колбэки `on_recv`/`on_event` и порт-колбэки (`tx`, `now_ms`, `rnd`,
`timer_arm`) выполняются **внутри** `poll`, т.е. под вашим мьютексом — не берите
мьютекс повторно и **не вызывайте функции библиотеки из колбэков** (библиотека
не реентерабельна), откладывайте работу (флаг/очередь) до возврата из `poll`.
`treenet_init` вызывается до старта потоков, мьютекс не нужен.

## 6. Роли

| Роль | Описание |
|---|---|
| `TREENET_ROLE_MASTER` | Корень DODAG. Rank = 0, нет родителя, всегда `connected`. |
| `TREENET_ROLE_NODE` | Обычный узел. Имеет родителя и маршрут к Master. |
| `TREENET_ROLE_REPEATER` | Инфраструктурный ретранслятор: как NODE, но при flooding ретранслирует с высшим приоритетом (нулевая задержка). |
| `TREENET_ROLE_LEAF` | Конечное устройство/датчик. Отправляет и принимает **свои** данные, но **не роутер**: не пересылает чужой трафик, не ретранслирует flooding и не может быть родителем для других узлов. |

## 7. Адресация

- `treenet_addr_t` — 32 бита.
- `0xFFFFFFFF` — broadcast, `0x00000000` — недействительный адрес.
- Адрес задаётся приложением в `treenet_config_t.addr` (например, из MAC/ID
  микросхемы). Библиотека не назначает адреса.
- `net_id` (16 бит) — логический идентификатор сети; кадры с другим `net_id`
  молча игнорируются (до обновления метрик — чужие узлы не попадают в таблицу
  соседей), что позволяет сосуществовать нескольким сетям на одном канале.

## 8. Точки расширения

- **Безопасность** (зарезервировано, в v0.1.0 не реализовано). Байт `sec` в
  заголовке и флаг `TN_FLAG_SEC` — заготовки. Порт может шифровать полезную
  нагрузку до `tx` и расшифровывать после `treenet_rx`.
- **Метрики.** `treenet_neighbors()` и `treenet_stats()` дают приложению доступ
  к живой оценке качества связи и счётчикам.

## 9. Ограничения текущей версии

- Хранение маршрутов — storing mode. Non-storing (source routing от Master) —
  направление развития для сетей > ~500 узлов.
- Нет шифрования и аутентификации (только точки расширения).
- Нет энергосбережения/sleep.
- Один Master на сеть.
